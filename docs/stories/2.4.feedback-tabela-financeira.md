# Story 2.4: Feedback de edição na tabela financeira e indicador de autosave

## Status

Draft

## Story

**As a** consultor que preenche a "Perda Recurso Mensal" de cada recurso,
**I want** ver de forma sutil quais valores foram recalculados após cada edição e saber com clareza se minhas alterações estão pendentes, sendo salvas, salvas ou com erro (com opção de tentar de novo),
**so that** eu confie que o que digitei foi persistido — e que o relatório PDF gerado em seguida reflete os valores atuais — sem que nenhuma animação atrapalhe a digitação.

## Acceptance Criteria

1. **Regressão — autosave já grava o valor atual (corrigido nesta branch):** a closure desatualizada de `triggerSave` (achado 30) foi corrigida em `9d19d19` — `triggerSave` lê `useMunicipioStore.getState()` no momento da chamada (`useAutoSave.ts:85`) — e a fila de autosave (`src/utils/filaSalvamento.ts`, `descarregarAutosave` exportado por `useAutoSave.ts:21`) garante que a edição ainda pendente é enviada ao desmontar a tabela (troca de rota/município/competência/"Limpar Seleções"), antes dos dois PDFs (`Dashboard.tsx` chama `await descarregarAutosave()`) e antes de uma nova consulta (`useConsultarDados.ts:34`) — commits `4c78e91`/`a14fe66`/`6118e28`. Esta story **valida** essa correção (Network) e não deve reintroduzir a closure desatualizada nem alterar a fila.
2. **Estados do autosave:** `useAutoSave` passa a expor, além dos campos atuais (`triggerSave`, `status`, `isSaving`, `isSaved`, `isError`, `error`), o estado `pending` (edição feita, aguardando o debounce — deriva de `temPendente()` da fila de autosave, já implementada em `utils/filaSalvamento.ts:22,67`, e exposta pelo hook), `lastSavedAt: Date | null` e `retry()` (reenvia o último payload **completo**, incluindo `itens`). O debounce continua 2000 ms; o payload `MunicipioEditadoCreate` já inclui o array `itens` (nome do plano, valor, origem, `regra_id`, `valor_sugerido` — `useAutoSave.ts:94-113`, stories 3.2/3.3) — esta story não deve alterar como `itens`/`origem` são montados, só garantir que `retry()` reenvia o payload como veio.
3. **Indicador de salvamento:** só o bloco "Status" (`FinancialTable.tsx:228-234`, dentro do `Space` maior que também contém o botão "Preencher automaticamente" e o contador "N registros", `:227-250`) é substituído por `SaveStatusIndicator`, **preservando** esse botão e o `onAplicado={() => triggerSave()}` do `PreenchimentoAutomatico` (`:255`) sem alterações. Textos do indicador: "Sem alterações" (idle), "Alterações pendentes…" (pending), "Salvando…" (saving), "Salvo às HH:MM" (saved, horário pt-BR) e "Erro ao salvar" + botão "Tentar novamente" (error, que chama `retry()`). A troca de estado usa `AnimatePresence` com fade ≤ 150 ms e o contêiner tem `role="status"` e `aria-live="polite"`.
4. **Destaque sutil após edição:** quando o valor de "Perda Recurso Mensal" de uma linha é confirmado e muda, as células derivadas da mesma linha (Potencial Mensal, Potencial Anual, Diferença Anual) exibem um destaque de fundo (`highlightFlash` de `src/theme/motion.ts`) que aparece e some em ≤ 600 ms. Não há destaque no carregamento inicial nem quando o valor não muda. **Preenchimento em lote:** quando "Preencher automaticamente" aplica várias linhas de uma vez (`PreenchimentoAutomatico.tsx:85-107`, chamando `setDadosEditados` uma única vez), as células derivadas de **todas** as linhas alteradas piscam juntas, uma única vez (não em sequência/stagger) — cada `FlashOnChange` reage independentemente à mudança do seu próprio valor.
5. **Sem roubar foco:** nenhuma animação é aplicada ao `CurrencyInput` nem ao `<tr>`/`<td>` da coluna editável; o foco, o cursor e o texto em digitação nunca são afetados; navegar com Tab entre inputs continua funcionando; não há `layout` animation dentro da `Table`.
6. **Mobile:** a visualização em cards (`MobileCardView`) é extraída para um componente de nível de módulo (deixa de ser recriada a cada render — hoje todos os cards e inputs são desmontados/remontados a cada alteração do store). Os cards entram com stagger (≤ 50 ms entre itens, 200 ms cada) apenas quando chega uma nova consulta, e os valores derivados recebem o mesmo destaque do AC 4. A barra "Status" + botão "Preencher automaticamente" (`FinancialTable.tsx:227-250`, achado 31) não transborda em 375 px (usar `wrap` no `Space` ou empilhar em coluna no mobile).
7. **Acessibilidade dos inputs:** cada `CurrencyInput` da tabela e dos cards recebe `aria-label` descritivo (ex.: "Perda recurso mensal — {nome do recurso}"); o `id` padrão duplicado `'currency-input'` deixa de ser usado sem prop.
8. **Semântica de cor da diferença:** a cor de "Diferença Anual" na tabela e no card mobile passa a ser consistente com `MetricsCards` (diferença > 0 = perda → vermelho/`danger`), **após confirmação do PO** (registrar a decisão no Change Log). Se o PO decidir o contrário, ajustar `MetricsCards` em vez da tabela.
9. Com `prefers-reduced-motion: reduce`: sem stagger nos cards mobile (inclusive quando o "Preencher automaticamente" altera várias linhas de uma vez); o destaque (individual ou em lote) vira troca instantânea de cor mantida por ~600 ms (sem animação) ou é omitido; o indicador troca de texto sem fade.
10. **Funcionalidade existente continua igual:** consulta de município; edição com `CurrencyInput` (Enter confirma, Esc cancela e restaura, blur confirma, botão limpar); recálculo imediato de MetricsCards; autosave com debounce de 2 s (inclusive a fila/retomada corrigidas nesta branch); "Preencher automaticamente" (abrir, revisar, aplicar); geração dos dois PDFs (já com o último valor salvo); login e admin.
11. `npx tsc -b` passa; lint dos arquivos alterados sem novos erros — `useAutoSave.ts` já tem 2 erros `no-explicit-any` pré-existentes (linhas 55 e 57, `onError: (err: any, ...)` e `context as any`): não aumentar (idealmente corrigir); projeto ≤ 16 erros; build de verificação em `/tmp`.
12. Plano de rollback documentado (Dev Notes).

Isso é o cenário de "preenchimento em lote" do AC 4/AC 9: todas as `FlashOnChange` das linhas alteradas devem piscar juntas nessa única atualização.

### Esboço do `FlashOnChange`
```tsx
import { useAnimate, useReducedMotion } from 'motion/react';
const [scope, animate] = useAnimate<HTMLSpanElement>();
const prev = useRef(value);
const reduce = useReducedMotion();
useEffect(() => {
  if (prev.current !== value && !reduce) {
    animate(scope.current, { backgroundColor: [highlightFlash.from, highlightFlash.to] }, { duration: 0.6, ease: 'easeOut' });
  }
  prev.current = value;
}, [value]);
return <span ref={scope} style={{ display: 'inline-block', borderRadius: 4, padding: '0 4px' }}>{children}</span>;
```
Animar só `backgroundColor` (não causa reflow, não mexe no foco).

### Restrições
- Proibido: animar `CurrencyInput`, usar `m.tr`/`motion.tr` via `components.body.row`, `layout`/`layoutId` na tabela, `AnimatePresence` em linhas da tabela.
- Não mudar o debounce (2000 ms), o endpoint `apiClient.upsertMunicipioEditado`, o formato do payload (`itens` incluído) nem a fila de autosave (`utils/filaSalvamento.ts`) — essa parte já está corrigida e coberta por `frontend/tests/filaSalvamento.test.ts` (`npm test`).
- A lógica otimista/rollback de cache em `useAutoSave.ts:33-66` deve ser mantida.
- Não alterar `PreenchimentoAutomatico.tsx` além de, se necessário, ajustar o que acontece **depois** de `aplicar()` (ex.: mensagem de sucesso) — a lógica de aplicar várias posições de uma vez (achado 32) é a mesma que alimenta o destaque em lote do AC 4.
